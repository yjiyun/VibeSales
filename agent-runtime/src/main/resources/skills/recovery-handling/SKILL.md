# Recovery Handling Skill

对应原工作流 `147282 U14-06`（恢复确认话术），配套判定来自 `114759 U14-01` /
`2603112 U14-04` / `2603107 U2-05`。

## 目标

用于正式项目第一版中的恢复判断链路，帮助主 Agent 在收到用户消息后，优先判断这条消息是在继续上一轮未完成任务，还是开启一个新的处理轮次。

## 触发时机

每轮对话开始前，编排层会先预取历史摘要、任务板、客户画像，并由 `RecoveryDetectionRule` 计算
“当前是否在续接上一轮未完成话题”。这些结构化结果会写入 `RuntimeContext`，再由
`Middleware.onSystemPrompt(...)` 追加到系统提示词。**这份 Skill 不需要、也不应该自己重新判断
是否续接**，只需要消费系统提示词里已经给出的结论，在措辞和语气上体现对应处理方式：

- 若结论是"续接"，参考下方"续接话术"续接客户之前的话题
- 若结论是"新话题"，按新一轮正常处理，不要主动假设存在未完成的历史话题

## 依赖信息

- 当前采用“编排层预取 + 系统提示词注入”模式，不直接调用 Tool
- 历史摘要来源：`getHistorySummary`
- 任务板快照来源：`getIntentQueue`
- 客户画像摘要来源：`getCustomerProfile`
- 恢复结论来源：`RecoveryDetectionRule`

## 恢复必须二次确认

`recoverMode` 固定为 `confirm_then_resume`，**不允许静默直接恢复**。
也就是说：不能默认客户就是在接上文，必须先用一句话把上文点出来让客户确认，再继续。

反例（禁止）：客户说「好的」，直接接着推上一轮的产品。
正例：「刚才咱们在说你 T 区出油那块，你是想接着看这个吗？」

## 续接话术

- 一句话点明上文是什么，让客户能"哦对"地想起来。
- 点上文要用**客户自己的说法**，不要用内部术语。
- 确认句要好回答，一个是或不是就能答。

## 绝不对客展示的技术串

历史摘要与任务板里会带内部状态串，命中下列任一子串的内容**不得出现在回复里**：

- `active`
- `待办`
- `主诉切换`
- `切换进入待办`

这些是给编排层看的，客户看到会一脸问号。

## 多个待办怎么选

任务板里可能有多条待办。择优由规则计算（优先级分绝对压过意图类型），结论会给你。
**你不要自己排序**，也不要一次问客户两个待办。

## 约束

- 不在 Skill 中直接固化关键硬规则
- 关键硬规则以下层代码或 Tool 为准
- 恢复结论缺失时按新话题处理，不要猜
