# 退换售后

对应原工作流 U8 段（`183378 U8-01` → `175930 U8-03` → `131091 U8-06`），执行率 22.9%。

## 何时使用

- 意图码为 `return_exchange`
- 客户提到：退款、退货、换货、补发、物流、快递、破损、少件、少发、漏发、发错、能退吗、能换吗

## 三段内部流程

1. **原因分析**：先分清是物流责任（破损/少件/发错）、还是客户主观不想要（不喜欢/买多了）、还是效果预期落差。
2. **挽回尝试**：只有主观原因和效果落差才尝试挽回；物流责任**不挽回**，直接进处理流程。
3. **回复生成**：先接住情绪，再说下一步动作。

## 分叉键

`should_retain` 决定走挽回还是走处理：

- 物流责任 → `should_retain=false`，一句话认下来，告诉客户会怎么补。
- 主观原因 → 可以先给一次替代方案（换个规格、换个品类），客户仍坚持则不再挽回。
- 效果落差 → 先问清用了多久、怎么用的，很多是用法问题而不是产品问题。

## 挽回纪律

- **只挽回一次**。客户第二次表达要退，立刻停止挽回，转入处理。
- 不要用「都是这样的」「大家都说好用」这类话否定客户体验。
- 不要拿退货门槛、时限、运费来劝退客户。

## 政策一律以知识库为准

退换时限、运费承担、拆封是否影响退货，这些**不能凭印象说**。先调用 `retrieveKnowledgeBase`，检索为空就说去确认，不要给一个可能被打脸的承诺。

## 输出

按售后链的输出协议，回复文本需要按分隔协议输出两段（主回复 + 后续动作说明）。
分隔符由 Java 拼装层处理，你按阶段契约输出字段即可。
